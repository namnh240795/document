1. Introduction

1.1 Purpose

This document defines the software requirements for the Authentication module of the Authentication System.

1.2 Scope

The Authentication module handles:

  • User registration with email or phone + password
  • User login with email or phone + password
  • Session and token management (access + refresh tokens)
  • Account verification via email and SMS
  • Password reset via email or phone/OTP
  • Role-based access control (RBAC)
  • User management (admin CRUD)

1.3 Module Dependencies

ModuleDependency TypeDescription
SMSAsync (RabbitMQ)Send verification SMS via SMS module
EMAILAsync (RabbitMQ)Send verification/reset emails via EMAIL module
LOGAsync (RabbitMQ)Publish auth events to Logger module

3. Functional Requirements

Req ID Module Requirement Use Case Priority Description
FR-001 AUTH User Registration UC-01 High System shall allow users to register with email or phone + password + name. Registered users receive the user system role by default.
FR-002 AUTH User Login UC-02 High System shall authenticate users via email or phone + password and return JWT tokens
FR-003 AUTH Logout UC-03 High System shall invalidate user session on logout
FR-004 AUTH Refresh Token UC-04 High System shall issue new access token using refresh token
FR-005 AUTH Reset Password (Email) UC-05 Medium System shall send password reset link to user's email via EMAIL module
FR-006 AUTH Reset Password (Phone) UC-06 Medium System shall send OTP to user's phone for password reset
FR-007 AUTH Change Password UC-07 Medium System shall allow authenticated users to change password
FR-008 AUTH Verify Email UC-08 High System shall send verification email via EMAIL module and verify via link
FR-009 AUTH Verify Phone UC-09 High System shall verify phone via OTP code
FR-010 AUTH Manage Users UC-10 Medium Admin shall be able to list, view, update, and delete users
FR-011 AUTH Manage System Roles UC-11 Medium Admin shall be able to manage system-level roles (user, super_admin) and assign them to users
FR-012 AUTH Social Authentication UC-12 High System shall allow users to sign in via social providers (Google, GitHub, etc.) and link/unlink social accounts
FR-013 AUTH Session Management UC-13 High System shall allow users to view, revoke, and manage active sessions across devices
FR-014 AUTH User Ban & Impersonation UC-14 Medium Admin shall be able to ban/unban users and impersonate users for support
FR-015 AUTH Organization Management UC-15 High System shall allow users to create, update, delete organizations, manage membership, and create/manage organization-level roles (HR, Candidate, Employer) with fine-grained permissions
FR-016 AUTH Team Management UC-16 Medium System shall allow creating teams within organizations and managing team membership
FR-017 AUTH Invitation Management UC-17 High System shall allow inviting members to organizations via email with token-based verification. Invitations include: SHA-256 hashed tokens (only hash stored in DB), configurable expiry (default 72 hours), duplicate detection (same email + role), and email delivery via EMAIL module
FR-018 AUTH Resend Invitation UC-18 Medium System shall allow the inviter to resend an invitation, generating a new token and invalidating the previous one. Expiry is reset to 72 hours from resend time
FR-019 AUTH Revoke Invitation UC-19 Medium System shall allow the inviter (owner) to revoke a pending invitation. Only the original inviter can revoke. Already accepted or revoked invitations cannot be revoked again
FR-020 AUTH Verify Invitation Token UC-20 High System shall provide a public endpoint (no auth required) to verify invitation token validity. Returns status: valid, expired, already accepted, or revoked. Expired invitations are auto-updated to expired status

4.1 UC-01: User Registration

AspectDescription
ActorGuest (unauthenticated user)
PreconditionsUser is not logged in; user does not have an existing account
Main Flow1. User navigates to registration page
2. User enters name, email, and password

4.17 UC-17: Invitation Management

AspectDescription
ActorOrganization admin / Invited user
PreconditionsAdmin is logged in; invitee has email address
Main Flow1. Admin invites user by email with role and optional team
2. System generates random token (crypto.randomBytes(32)), computes SHA-256 hash
3. System stores only the hash in auth_invitations (token_hash column)
4. System constructs invite URL: {FRONTEND_DOMAIN}/invitations/verify?token={raw_token}
5. System sends invitation email via EMAIL module with the invite URL
6. Invitee receives email, clicks invitation link
7. Invitee's browser calls GET /organization/verify-invitation?token={raw_token} (public)
8. System hashes token, looks up by hash, returns validity status
9. Invitee accepts or rejects invitation
Alternative Flows2a. Duplicate pending invitation (same email + role) → System returns 409 Conflict
8a. Token expired → System auto-updates status to EXPIRED, returns 410
8b. Invitation already accepted → System returns status "accepted"
8c. Invitation revoked → System returns status "revoked"
PostconditionsInvitation sent with secure token; user added to organization (if accepted)
Related FRFR-017, FR-020

4.18 UC-18: Resend Invitation

AspectDescription
ActorOrganization admin (original inviter)
PreconditionsAdmin is logged in; invitation exists and is pending
Main Flow1. Admin selects invitation to resend
2. System generates new token (old token invalidated)
3. System resets status to PENDING, extends expiry by 72 hours
4. System sends new invitation email via EMAIL module
5. System returns success response
Alternative Flows1a. Invitation already accepted → System returns 409
1b. Invitation not found → System returns 404
1c. Requester is not the original inviter → System returns 403
PostconditionsNew token generated; old token invalidated; email sent
Related FRFR-018

4.19 UC-19: Revoke Invitation

AspectDescription
ActorOrganization admin (original inviter)
PreconditionsAdmin is logged in; invitation exists and is pending
Main Flow1. Admin selects invitation to revoke
2. System verifies ownership (only original inviter can revoke)
3. System updates status to REVOKED
4. System emits invitation.revoked event
5. System returns success response
Alternative Flows2a. Invitation already accepted → System returns 409
2b. Invitation already revoked → System returns 409
2c. Requester is not the original inviter → System returns 403
PostconditionsInvitation revoked; token no longer valid
Related FRFR-019

4.20 UC-20: Verify Invitation Token

AspectDescription
ActorInvited user (unauthenticated)
PreconditionsUser received invitation email with token URL
Main Flow1. User clicks invitation link in email
2. Frontend calls GET /organization/verify-invitation?token={raw_token}
3. System computes SHA-256 hash of token
4. System looks up invitation by token_hash
5. System checks status and expiry
6. If expired: auto-updates status to EXPIRED
7. System returns validity status with invitation details
Alternative Flows4a. Token not found → System returns 404
4b. Already accepted → System returns { valid: false, reason: "accepted" }
4c. Expired → System returns { valid: false, reason: "expired" }
4d. Revoked → System returns { valid: false, reason: "revoked" }
PostconditionsToken validity confirmed; user can proceed to accept/reject
Related FRFR-020
