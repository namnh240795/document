2.2 Key Design Decisions

#DecisionRationaleResolves
1Presigned URL upload (client-side) Reduces server load; no need to buffer file content in backend; supports large files FR-001, NFR-004
2Soft delete with event-driven S3 cleanup Allows rollback; decouples metadata cleanup from physical storage cleanup; audit trail FR-004
3Separate file_db database Independent scaling; isolated failure domain; clean separation of concerns NFR-003
4Hierarchical S3 key structure Supports multi-tenancy; simplifies access control; efficient listing by prefix FR-005
5TEMP status for in-progress uploads Prevents phantom files; enables automatic cleanup of abandoned uploads FR-006
6Category-based validation Enforces file type/size rules per use case; prevents abuse FR-001, NFR-005

6. Integration Flows

6.1 File Upload Flow

Activity Diagram

Figure 2: File Upload Activity Flow

Sequence Diagram

Figure 3: File Upload Integration Flow

Flow Description:

  1. Client sends POST /files/presigned-url with file metadata
  2. FileService validates category MIME types and size limits
  3. StorageKeyUtil generates unique S3 key: {employer_id}/{user_id}/{category}/{uuid_filename}
  4. S3Util generates presigned PUT URL (15 min expiry)
  5. FileService inserts sys_files record with status TEMP
  6. Response sent to client with presigned URL
  7. Client uploads file directly to S3 via presigned URL (PUT)
  8. Client calls POST /files/confirm with file_id
  9. FileService updates status from TEMP to ACTIVE
  10. File record returned to client

6.2 File Download Flow

Activity Diagram

Figure 4: File Download Activity Flow

Sequence Diagram

Figure 5: File Download Integration Flow

Flow Description:

  1. Client sends GET /files/:id/download-url
  2. AuthGuard validates JWT token
  3. FileGuard checks access (owner or org admin/HR)
  4. FileService looks up sys_files record
  5. S3Util generates presigned GET URL (15 min expiry)
  6. Response sent to client with download URL
  7. Client downloads file from S3 via presigned URL (GET)

6.3 File Delete Flow

Activity Diagram

Figure 6: File Delete Activity Flow

Sequence Diagram

Figure 7: File Delete Integration Flow

Flow Description:

  1. Client sends DELETE /files/:id
  2. AuthGuard validates JWT token
  3. FileGuard checks ownership or admin role
  4. FileService sets status to DELETED and deleted_at timestamp
  5. FileService emits file.deleted event to RabbitMQ
  6. FileWorker consumes event
  7. FileWorker calls S3Util to delete S3 object by storage_key
  8. Success response sent to client

6.4 Temp File Cleanup Flow

Activity Diagram

Figure 8: Temp File Cleanup Activity Flow

Sequence Diagram

Figure 9: Temp File Cleanup Integration Flow

Flow Description:

  1. NestJS Scheduler triggers cron job every 1 hour
  2. TempCleanupJob queries sys_files where status=TEMP AND created_at < NOW() - 24h
  3. For each expired TEMP file:
    • Delete sys_files record
    • Emit file.temp_cleanup event with storage_key
  4. FileWorker consumes events and deletes S3 objects

7.2 Presigned URL Security

  • Presigned URLs use SigV4 signing with short expiration (15 minutes)
  • URLs are single-use in practice (though technically reusable within expiry window)
  • No file content passes through the application server (direct S3 transfer)
  • S3 bucket policy enforces HTTPS-only access
  • CORS configuration allows only the application domain
