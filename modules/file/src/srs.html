1. Introduction

1.1 Purpose

This document defines the software requirements for the File Management module of the Job Portal System.

1.2 Scope

The File Management module handles:

  • File upload via presigned URLs (client-side direct upload to S3)
  • File download via presigned URLs with expiration
  • File listing with filtering by user, employer, and category
  • Soft delete with event-driven S3 cleanup
  • File access control based on ownership and RBAC
  • Automatic cleanup of temporary/orphaned files

3. Functional Requirements

Req ID Module Requirement Use Case Priority Description
FR-001 FILE Upload File UC-01 High System shall generate presigned upload URL or support direct multipart upload. Client uploads directly to S3. System stores file metadata on confirmation.
FR-002 FILE Download File UC-02 High System shall generate presigned download URL with configurable expiration. Download URL is valid for 15 minutes by default.
FR-003 FILE List Files UC-03 Medium System shall query files by user, employer, and category with pagination support. Results are filtered by access control.
FR-004 FILE Delete File UC-04 Medium System shall soft-delete file metadata and emit an event for asynchronous S3 object cleanup. File status set to DELETED.
FR-005 FILE File Access Control UC-02 High System shall validate file ownership or RBAC permission before generating download URLs. Users can only access their own files unless they have admin/HR role in the organization.
FR-006 FILE Temp File Cleanup - Medium System shall run a scheduled job (cron) to delete TEMP files older than 24 hours. Emits cleanup events for S3 physical deletion.

4.1 UC-01: Upload File

AspectDescription
ActorAuthenticated user
PreconditionsUser is logged in; user has a valid session token
Main Flow1. User selects a file to upload (e.g., resume, avatar)
2. Client sends upload request with original_name, mime_type, and category
3. System validates file type and size against category limits
4. System generates presigned S3 upload URL and creates file record with status TEMP
5. Client uploads file directly to S3 using presigned URL
6. Client confirms upload completion via POST /files/confirm
7. System updates file status to ACTIVE
8. System returns file record
Alternative Flows3a. Invalid file type → System returns 400 Validation Error
3b. File too large → System returns 413 Payload Too Large
5a. S3 upload fails → Client can retry with same presigned URL
6a. Confirm not received within 24h → Temp file cleanup removes record
PostconditionsFile uploaded to S3; file metadata stored in database with ACTIVE status; file accessible via download URL
Related FRFR-001

4.2 UC-02: Download/View File

AspectDescription
ActorAuthenticated user
PreconditionsUser is logged in; file exists with ACTIVE status
Main Flow1. Client requests file download by file ID
2. System validates user has access (owner or org admin/HR)
3. System generates presigned S3 download URL (15-minute expiry)
4. System returns download URL, expiration, and file name
5. Client downloads file from S3 via presigned URL
Alternative Flows2a. User not authorized → System returns 403 Forbidden
2b. File not found or DELETED → System returns 404 Not Found
4a. Download URL expired → Client requests new URL
PostconditionsFile downloaded by authorized user; presigned URL expires after 15 minutes
Related FRFR-002, FR-005

4.3 UC-03: List User Files

AspectDescription
ActorAuthenticated user
PreconditionsUser is logged in
Main Flow1. Client requests file list with optional filters (user_id, employer_id, category)
2. System applies access control filters
3. System queries sys_files with pagination
4. System returns file list with total count
Alternative Flows2a. No filters provided → System returns current user's files
2b. Employer filter → System returns all files for that employer (admin/HR only)
PostconditionsPaginated file list returned with metadata (no file content)
Related FRFR-003, FR-005

4.4 UC-04: Delete File

AspectDescription
ActorAuthenticated user (file owner or admin)
PreconditionsUser is logged in; file exists with ACTIVE status
Main Flow1. Client requests file deletion by file ID
2. System validates user is file owner or has admin role
3. System sets file status to DELETED and deleted_at timestamp
4. System emits file.deleted event to message queue
5. FileWorker picks up event and deletes S3 object
6. System returns success response
Alternative Flows2a. User not authorized → System returns 403 Forbidden
2b. File already DELETED → System returns 404 Not Found
5a. S3 deletion fails → Worker retries with exponential backoff
PostconditionsFile metadata soft-deleted; S3 object queued for physical deletion; file no longer accessible
Related FRFR-004, FR-005
