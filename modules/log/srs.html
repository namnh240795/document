1. Introduction

1.1 Purpose

This document defines the software requirements for the Logger module of the Authentication System.

1.2 Scope

The Logger module handles:

  • Centralized event logging from all services via RabbitMQ
  • Storage in OpenSearch for full-text search and analytics
  • Log querying and filtering
  • Real-time monitoring dashboards

1.3 Module Dependencies

Receives events from: AUTH, SMS, EMAIL (all modules publish logs)

4. Use Cases

UC-01: Ingest Log Events

AspectDescription
ActorAll services (AUTH, SMS, EMAIL - producers)
PreconditionsRabbitMQ queue log.events is available; OpenSearch is running
Main Flow1. Service performs operation (login, send SMS, etc.)
2. Service publishes log event to RabbitMQ queue log.events
3. Log Consumer receives event from queue
4. Consumer validates event schema
5. Consumer indexes event to OpenSearch (index: log-events)
6. Event is now searchable and available for queries
Alternative Flows4a. Invalid event schema → Consumer logs error, event DLQ
5a. OpenSearch unavailable → Event buffered in RabbitMQ, retried
5b. Indexing fails → Consumer retries with exponential backoff
PostconditionsLog event stored in OpenSearch; available for search and analytics
Related FRFR-001

UC-02: Query Logs

AspectDescription
ActorAdmin user, Operations team
PreconditionsUser is authenticated with admin role; logs exist in OpenSearch
Main Flow1. User navigates to log search page
2. User applies filters (level, source, time range, search term)
3. System queries OpenSearch with filters
4. System returns paginated results
5. User can click on event to view full details
Alternative Flows3a. No results found → System returns empty array with total: 0
3b. Query timeout → System returns 500 QUERY_FAILED
4a. User exports results (CSV/JSON)
PostconditionsSearch results returned; user can analyze log data
Related FRFR-002

UC-03: Log Analytics

AspectDescription
ActorAdmin user, Operations team
PreconditionsUser is authenticated with admin role; sufficient log data exists
Main Flow1. User navigates to analytics dashboard
2. User selects time range and metrics
3. System queries OpenSearch aggregations
4. System returns analytics data (error rates, response times, by source)
5. System displays charts and graphs
Alternative Flows3a. Aggregation query fails → System returns 500
4a. Insufficient data → System shows partial results with warning
PostconditionsAnalytics dashboard displayed; insights available
Related FRFR-003

UC-04: Real-time Monitoring

AspectDescription
ActorOperations team, On-call engineer
PreconditionsUser is authenticated; WebSocket connection available
Main Flow1. User connects to WebSocket /ws/logs with JWT token
2. User specifies filters (level, source)
3. System establishes WebSocket connection
4. As new log events are indexed, System streams them to connected clients
5. User sees real-time log feed
Alternative Flows1a. Invalid token → Connection rejected with 401
3a. Connection dropped → Client auto-reconnects
4a. High event volume → System applies backpressure
PostconditionsReal-time log streaming active; user monitors live events
Related FRFR-004
