1. Introduction

1.1 Purpose

This document defines the software requirements for the Authentication System. It provides a comprehensive set of functional and non-functional requirements for user registration, login, session management, and role-based access control using Better Auth with NestJS, PostgreSQL, and Drizzle ORM.

1.2 Scope

The Authentication System handles:

  • User registration with email or phone number + password
  • User login with email or phone number + password
  • Session and token management (access token + refresh token)
  • Account verification via email and SMS (event-driven with RabbitMQ)
  • Idempotent verification requests (prevent duplicate sends via Redis)
  • SMS delivery logging and tracking (dedicated SMS database)
  • Password reset via email or phone/OTP
  • Role-based access control (RBAC)
  • User management (admin CRUD)

3.2 UC-01: User Registration

FieldValue
Requirement IDsFR-001
ActorUser
PreconditionUser is not authenticated
PostconditionUser account created, verification email/OTP sent

Main Flow

  1. User provides email (or phone) + password + name
  2. System validates input format
  3. System checks if email/phone already exists
  4. System hashes password with bcrypt
  5. System creates user record in auth_users
  6. System creates account record in auth_accounts (provider: credential)
  7. System sends verification email or OTP to phone
  8. System returns success response

Alternative Flow

  1. Email/phone already exists: return 409 Conflict

Exception Flow

  1. Invalid input: return 400 Validation Error
  2. Server error: return 500 Internal Error

3.3 UC-02: User Login

FieldValue
Requirement IDsFR-002
ActorUser
PreconditionUser account exists
PostconditionUser authenticated, session created, tokens issued

Main Flow

  1. User provides email (or phone) + password
  2. System parses identifier type (email or phone)
  3. System queries auth_users by email or phone
  4. System verifies password via bcrypt compare
  5. System creates session in auth_sessions
  6. System generates access token (JWT) + refresh token
  7. System returns tokens and user info

Exception Flow

  1. User not found or wrong password: return 401 Invalid Credentials
  2. Account not verified: return 403 Account Not Verified

3.13 UC-12: Request Account Verification

FieldValue
Requirement IDsFR-012
ActorUser / System (on registration)
PreconditionUser exists, email or phone not yet verified
PostconditionVerification email/SMS sent asynchronously via RabbitMQ

Main Flow

  1. User requests account verification (or triggered on registration)
  2. System generates idempotency key from user_id + channel (email/sms)
  3. System checks Redis for existing idempotency key
  4. If key exists and not expired: return "Verification already sent" (idempotent response)
  5. If no key: set idempotency key in Redis with 5-minute TTL
  6. System generates verification token/OTP
  7. System stores token in auth_verification table
  8. System publishes verification event to RabbitMQ queue
  9. Verification Worker consumes event, sends email/SMS via provider
  10. Worker logs delivery status to sms_logs (SMS) or auth_verification (email)
  11. System returns success response

Alternative Flow

  1. Idempotency key exists: return 200 with "already sent" message (no duplicate)

Exception Flow

  1. SMS/Email provider fails: log failure in sms_logs, retry via RabbitMQ dead-letter queue
  2. Redis unavailable: bypass idempotency check, log warning, proceed with send

3.14 UC-13: Resend Verification

FieldValue
Requirement IDsFR-013
ActorUser
PreconditionUser exists, previous verification expired or not received
PostconditionNew verification email/SMS sent with rate limiting

Main Flow

  1. User requests to resend verification
  2. System checks Redis rate limit key: resend_verify:{user_id}:{channel}
  3. If rate limit exceeded (1 request per 60 seconds): return 429 Too Many Requests
  4. System invalidates old verification token in auth_verification
  5. System follows same flow as UC-12 (idempotency + RabbitMQ)
